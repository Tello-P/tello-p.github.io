Embedded Qubit Engine

Q1.14 fixed-point quantum simulator in C · AVR / Arduino · live trace debugger

The idea

Quantum simulators are built out of floating-point complex numbers. An ATmega328P has no floating-point unit — no double, no sqrt(), no hardware divide, 2 KB of RAM and an 8-bit ALU. Every multiply is a subroutine call. So the question was simple: how much real quantum mechanics survives if you take all of that away?

The answer is a working simulator in under 300 lines of C — superposition, entanglement, interference, Grover's algorithm and probabilistic measurement — where the largest number the machine ever handles is an int16_t. There is no library underneath it. Every piece of maths in it had to be built by hand, and that is really what the project is.

Built from scratch

A number format. Amplitudes are Q1.14 fixed-point: one sign bit, one integer bit, fourteen fractional bits, so 1.0 is literally the integer 16384. A complex amplitude is two int16_t — four bytes. An entire 4-qubit register is 64 bytes, and the whole state pool is statically allocated, because there is no malloc worth trusting on a chip this size.

The multiply, in AVR assembly. Multiplying two Q1.14 values means a 16×16→32-bit product shifted back down by 14, with rounding. Written in C that is a slow int32_t detour. So fp_mul() drops into inline assembly and does it with the AVR's MULS/MULSU instructions, assembling the partial products by hand and replacing the 14-bit shift with two rotates through the carry — because on this core a shift by 16 is free and a shift by 14 is not. A portable C version sits behind an #ifdef so the same file still builds on a PC.

No square root. The Hadamard gate needs 1/√2, and there is no sqrt() to call. It ships as a constant — Q16_INV_SQRT2, the integer 46341. It began life as the Q1.14 version, 11585, doing double duty as the renormalisation factor after a measurement as well; both of those turned out to be wrong in ways worth keeping the receipts for. Measurement now divides by the probability that actually survived the collapse, and the gate keeps its scale in Q1.16 — what it costs, below, is where the norm gave that away.

Randomness. Measurement has to actually be random, and rand() is not something you want on a microcontroller. The core carries its own 64-bit SplitMix-style generator and folds its output down into a Q1.14 fraction, so collapse is decided by an integer comparison against the accumulated probability. Seed it and the same circuit collapses the same way every time — which is what makes the debugger reproducible.

Gates without matrices. The textbook approach applies a 2n×2n matrix to the state vector. That is unaffordable here, so gates are implemented as bit-mask butterflies: for a target qubit, walk the state indices, pair each i with i | mask, and touch only that pair. X and CNOT become pure swaps — no arithmetic at all. It is O(2n) per gate with no allocation and no temporaries.

What it costs

Fourteen fractional bits is not much room. Every gate rounds, and the rounding accumulates: the norm ⟨ψ|ψ⟩ drifts away from 1 as a circuit gets deeper. Rather than hide that, the debugger puts it on screen as a live drift readout — the honest error budget of the whole design, visible gate by gate. Measuring it was the point of building the tracer in the first place.

And measuring it caught something. The drift on a deep circuit was not rounding noise at all — it was one constant. Hadamard scaled by Q14_INV_SQRT2 = 11585, but the exact value is 16384/√2 = 11585.2375, and that missing 0.2375 makes H a contraction rather than a rotation: it takes 2·(11585/16384)² = 0.9999590 of the norm on every application, always in the same direction. A Grover iteration is mostly Hadamards — the diffuser runs an H layer on the way in and another on the way out — so six iterations on four qubits is 52 H gates, and 0.999959052 = 0.997870. The engine measured 0.997873. The constant accounted for the drift almost to the last digit; unbiased rounding would have random-walked instead of decaying.

11585 already is the closest Q1.14 can get, so the fix was not a better 14-bit constant — it was to stop keeping the scale in Q1.14 at all. The gate multiplies into an int32 anyway, so H now scales by Q16_INV_SQRT2 = 46341 and shifts by 16. Sixteen bits is the ceiling: |a ± b| ≤ 16384√2 = 23170 for a normalised pair, and 23170 × 46341 leaves half of int32 spare, where Q1.17 would sit on the overflow boundary. The state is still Q1.14 — only the scale got wider — and the AVR assembly is untouched, because apply_gate_h never called fp_mul.

The same source compiles twice — avr-gcc for the Arduino sketch, GCC for the host test suite — so the fixed-point results can be diffed between the 8-bit target and the desktop. On an ATmega328P at 16 MHz a gate takes about 175 µs.

The debugger

The demo is not a re-implementation in JavaScript. The same C is compiled a third way, to run inside the browser tab, and instrumented with tracing macros that compile to nothing in the firmware build. You assemble a circuit, run it, and scrub back and forward through the recorded execution: the raw Q1.14 state vector, the Bloch sphere of each qubit, and the exact line of C currently executing all move together, driven by __LINE__ values the core itself emitted.

A parity check runs seven circuits through the native binary and the in-browser build and compares the traces byte for byte, so what the browser shows is provably what the microcontroller does.
