Rotating a machine's network identity, one ioctl and one injected frame at a time

A Linux utility that randomises a NIC's hardware address and hand-builds the DHCP DISCOVER that follows it.

Two identifiers name you on a LAN, and they live at different layers. PrivIP rewrites the first through the kernel's ioctl configuration interface, then assembles a 292-byte Ethernet frame in a stack buffer and puts it on the wire with pcap_inject() — no socket, no kernel UDP stack, no DHCP client. This is a byte-level walkthrough of how it does that: every field, the exact bytes, and how the work divides between the tool and the operating system.

01 The problem

Two addresses identify you on a LAN, and they live at different layers

When a laptop joins a network it presents two identifiers. The first is the MAC address — 48 bits burned into the NIC, visible to every device in the broadcast domain, never routed past the first hop. The second is the IP address — leased from a DHCP server, and in practice keyed to the MAC that asked for it.

A captive portal that counts your 30 free minutes remembers a MAC. A DHCP server that hands you the same 192.168.1.47 every morning does so because it remembers a MAC. Change the first identifier and the second follows; the network sees a device it has never met.

PrivIP does exactly that, in two moves. It draws a fresh random hardware address and installs it through the kernel's ioctl configuration interface, then — instead of asking the system's DHCP client to renew — it builds a 292-byte Ethernet frame in a stack buffer and shoves it onto the wire with pcap_inject().

Layer 2

Randomised hardware address — two bits of octet 0 are fixed by the standard.

Layer 3

Leased address, re-solicited by a hand-built DHCP DISCOVER broadcast.

Privilege

2 caps

cap_net_raw to inject, cap_net_admin to reconfigure the link.

Why not just call dhclient

You could. The point of the exercise is that the DHCP client here is not a client in the OS sense — there is no AF_INET socket, no bind() to port 68, no kernel UDP stack involvement on transmit. The frame is assembled byte by byte and handed to the driver. That makes it a teaching artifact for packet construction as much as a privacy tool.

03 Entry point

Twenty lines that set the whole sequence

/* core/main.c */
int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "Incorrect argument number, just one interface please\n");
        return 1;
    }

    if (changeMac(2, argv) != 0) {
        fprintf(stderr, "MAC change failed, aborting\n");
        return 1;
    }

    /* DISCOVER, and retransmit once if the first attempt times out */
    if (dhcpClientRenew(2, argv) != 0 && dhcpClientRenew(2, argv) != 0) {
        fprintf(stderr, "No DHCP offer received\n");
        return 1;
    }

    return 0;
}

Both subsystems take (int argc, char **argv) rather than a plain interface string. That is a deliberate shim: dhcpClient.c began as Samuel Jacob's BSD-licensed Simple DHCP Client, whose main() was renamed to dhcpClientRenew() with its CLI parsing left intact. So the interface name arrives as argv[1] in both, and both still carry their own usage string.

The exit code means something

Each step's return value is checked and propagated. If the MAC rewrite fails — wrong interface name, missing CAP_NET_ADMIN, a driver that refuses SIOCSIFHWADDR — the program says so on stderr and exits 1 without broadcasting anything from the old address. The short-circuit && on the second line is a retransmission: the second DISCOVER only runs if the first returned non-zero, which after section 08 means "no offer inside ten seconds".

04 MAC rotation

Three ioctls on a throwaway datagram socket

There is no syscall named "set MAC address". Link configuration on Linux rides on ioctl() against any socket file descriptor — the socket is never used for traffic, it exists only as a handle into the networking subsystem. The whole module opens socket(AF_INET, SOCK_DGRAM, 0) and issues requests against it.

The request payload is struct ifreq: a fixed 16-byte interface name (IFNAMSIZ) followed by a large union whose active member depends on which request code you pass.

Step 1 — take the link down SIOCSIFFLAGS

ioctl(sock, SIOCGIFFLAGS, &ifr);      // read current flags
if (state) ifr.ifr_flags |=  IFF_UP;
else       ifr.ifr_flags &= ~IFF_UP;
ioctl(sock, SIOCSIFFLAGS, &ifr);      // write them back

Read-modify-write, not blind assignment — clobbering the flag word would drop IFF_BROADCAST, IFF_MULTICAST and friends. The link must be administratively down first: most drivers return EBUSY from SIOCSIFHWADDR on a running interface, because the address is programmed into the hardware receive filter. Every error path in the file closes the socket before returning -1.

Step 2 — draw a new address and install it SIOCSIFHWADDR

static void randomizeMac(unsigned char *mac) {
    int i;

    for (i = 0; i < 6; i++)
        mac[i] = (unsigned char)(rand() & 0xFF);

    mac[0] = (mac[0] & 0xFC) | 0x02;   // LAA set, multicast cleared
}

/* ... in randomizeAndSetMac() ... */
ioctl(sock, SIOCGIFHWADDR, &ifr);              // read, only to print it
memcpy(currentMac, ifr.ifr_hwaddr.sa_data, 6);

srand((unsigned int)(time(NULL) ^ getpid()));
randomizeMac(newMac);

ifr.ifr_hwaddr.sa_family = ARPHRD_ETHER;
memcpy(ifr.ifr_hwaddr.sa_data, newMac, 6);
ioctl(sock, SIOCSIFHWADDR, &ifr);

All six octets are drawn fresh, so the vendor prefix of the real card never survives the rotation and two successive addresses cannot be linked to each other. The masking on octet 0 is the part the standard fixes for you: bit 0 is the multicast bit and the kernel rejects a multicast source address outright, so it is cleared; bit 1 is the locally-administered bit, set to declare that these 46 remaining random bits are not a registered OUI assignment. Hence (mac[0] & 0xFC) | 0x02 — clear the low two, then set exactly one of them.

sa_family must be set to ARPHRD_ETHER (1) on the way in or the kernel rejects the request with EINVAL; the getter leaves it populated, but the code sets it explicitly anyway.

Unlinkable and anonymous are not the same goal

There is a real choice in those 46 bits. Keeping the vendor prefix and varying the rest leaves an address that still looks like a normal card from a known manufacturer — but successive addresses share a prefix, and anything that logs them can chain the sessions together. Drawing all six octets fresh breaks that chain completely, at the cost of an address that belongs to no registered vendor. PrivIP takes the second trade, which is the right default on a public network where nothing about you was known to begin with.

Step 3 — bring it back up

The same setInterfaceState(iface, 1). If the rewrite in step 2 failed, changeMac() still calls it before returning non-zero — a failed rotation must not leave the interface administratively down. On Wi-Fi this is where reality intrudes: taking wlan0 down tears down the association, and on a NetworkManager system the daemon will notice the carrier flap and start its own reconnect — potentially reprogramming the MAC (NM's own wifi.cloned-mac-address policy) and running its internal DHCP client. The C code has no idea any of that is happening.

05 The frame

Building outward from the middle of a 4 KB stack buffer

The transmit path is written inside-out, and the ordering is load-bearing. A single u_char packet[4096] lives on dhcp_discovery()'s stack; three pointers are computed into it at fixed offsets, and each layer's writer both fills its header and grows a shared length counter.

static int dhcp_discovery(u_int8_t *mac)
{
    int len = 0;
    u_char packet[4096];

    ip_header  = (struct ip *)      (packet + sizeof(struct ether_header));
    udp_header = (struct udphdr *)  ((char *)ip_header  + sizeof(struct ip));
    dhcp       = (dhcp_t *)          ((char *)udp_header + sizeof(struct udphdr));

    len = fill_dhcp_discovery_options(dhcp);     // +10  → 10
    dhcp_output(dhcp, mac, &len);                // +240 → 250
    udp_output(udp_header, &len);                // +8   → 258
    ip_output(ip_header, &len);                  // +20  → 278
    ether_output(packet, mac, len);              // +14  → 292, inject
    return 0;
}

Payload first, headers after — the same discipline a kernel uses, because every header needs the length of everything beneath it. ip_output() cannot fill ip_len until UDP has added its 8 bytes, and UDP cannot fill uh_ulen until the BOOTP body and its options are sized. Every one of the 292 bytes is written by one of those five calls, so nothing uninitialised from the stack reaches the wire.

Options are written before the header is zeroed

Look closely at the first two calls. fill_dhcp_discovery_options() writes into dhcp->bp_options[] — a zero-length flexible array member sitting at byte 240 of the struct. Then dhcp_output() runs memset(dhcp, 0, sizeof(dhcp_t)), which clears bytes 0–239 only. The options survive because sizeof(dhcp_t) stops exactly where they begin. Reverse those two lines and the packet still transmits, silently, with its options intact but its BOOTP header wiped — a bug that would only show up on the wire.

Each writer, in the order they run

fill_dhcp_option — the TLV primitive DHCP

static int fill_dhcp_option(u_int8_t *packet, u_int8_t code,
                            u_int8_t *data, u_int8_t len)
{
    packet[0] = code;
    packet[1] = len;
    memcpy(&packet[2], data, len);
    return len + (sizeof(u_int8_t) * 2);
}

Classic tag-length-value, returning bytes consumed so the caller can advance its cursor. Two options are emitted through it — message type 53 = DISCOVER, and parameter-request-list 55 asking for subnet mask, router, DNS and domain name — followed by the terminator, which is written directly as a single byte because option 255 carries neither length nor value:

dhcp->bp_options[len++] = MESSAGE_TYPE_END;    // bare 0xFF, per RFC 2132

There is deliberately no option 50. A requested-IP field in a DISCOVER is only meaningful when the client is asking for a lease it already held; naming a fixed address on a network you have just joined is at best ignored and at worst a claim on someone else's address.

udp_output — the alignment nudge UDP

if (*len & 1) *len += 1;              // pad payload to even
*len += sizeof(struct udphdr);
udp_header->uh_sport = htons(68);
udp_header->uh_dport = htons(67);
udp_header->uh_ulen  = htons(*len);
udp_header->uh_sum   = 0;             // legal on IPv4

The odd-length pad exists because the one's-complement checksum routine consumes 16-bit words. Here it is dead code — 240 + 10 = 250 is already even — but it is the correct instinct. A zero UDP checksum is permitted over IPv4 and means "not computed"; over IPv6 it would be illegal.

ip_output — a hand-rolled IPv4 header IPv4

ip_header->ip_hl  = 5;                // 5 × 4 = 20 bytes, no options
ip_header->ip_v   = IPVERSION;        // 4
ip_header->ip_tos = 0x10;             // low delay
ip_header->ip_len = htons(*len);      // 278
ip_header->ip_id  = htons(0xffff);
ip_header->ip_off = 0;
ip_header->ip_ttl = 16;
ip_header->ip_p   = IPPROTO_UDP;
ip_header->ip_sum = 0;
ip_header->ip_src.s_addr = 0;             // 0.0.0.0, we have no lease
ip_header->ip_dst.s_addr = 0xFFFFFFFF;    // 255.255.255.255
ip_header->ip_sum = in_cksum((unsigned short *)ip_header, sizeof(struct ip));

Source 0.0.0.0 is mandatory here and is precisely why this cannot go through a normal socket: the host has no address yet, so it identifies itself only by the chaddr field inside the DHCP body. Note the checksum field is zeroed before being summed — required, since the checksum covers itself.

in_cksum() is the FreeBSD one's-complement routine, verbatim: accumulate 16-bit words into a 32-bit sum, fold the carries down twice, invert. For this header the result is 0xA9C8.

ether_output — and out L2

memcpy(eframe->ether_shost, mac, ETHER_ADDR_LEN);
memset(eframe->ether_dhost, -1,  ETHER_ADDR_LEN);   // ff:ff:ff:ff:ff:ff
eframe->ether_type = htons(ETHERTYPE_IP);
len += sizeof(struct ether_header);
result = pcap_inject(pcap_handle, frame, len);

memset(dst, -1, 6) is the idiomatic way to write the broadcast address: -1 truncated to unsigned char is 0xFF. pcap_inject() hands the finished 292 bytes straight to the driver's transmit queue — no routing lookup, no ARP, no kernel checksum offload. Whatever is in the buffer is what leaves the machine.

06 Byte layout

Where every field lands in the 292-byte frame

The BOOTP fixed header is 236 bytes, followed by the 4-byte magic cookie, followed by variable options — which puts bp_options[0] at offset 240 within the DHCP body, exactly as RFC 2131 requires. The struct in dhcpClient.c reproduces that layout with no padding because every member is naturally aligned; sizeof(dhcp_t) is 240 on the nose.

The one field that skips htonl, on purpose

dhcp->xid = dhcp_xid is a plain 32-bit store, so on a little-endian host the transaction ID appears on the wire in reverse byte order — which is exactly why you can read d7 c1 3a 8f in the dump below for a value of 0x8f3ac1d7. It is the correct amount of work: xid is an opaque token the server echoes back verbatim, and the comparison on receipt is against the same host-order variable. Byte order only matters for fields somebody else has to interpret.

07 Hexdump

The exact bytes that leave the NIC

Captured by linking dhcpClient.c against a stub pcap_inject() that dumps its buffer instead of transmitting, with the randomised address fixed at 9a:4f:27:e3:08:1c and the transaction ID at 0x8f3ac1d7. Sixteen bytes of chaddr, six of them meaningful

dhcp_output() copies exactly ETHER_ADDR_LEN bytes into a 16-byte field and lets the preceding memset(dhcp, 0, sizeof(dhcp_t)) supply the ten zero bytes of padding you can see at 0x4c–0x55. The obvious-looking alternative — copying DHCP_CHADDR_LEN, the size of the destination — reads ten bytes past the end of a u_int8_t mac[6] on the caller's stack and broadcasts them to every host in the domain. The field's own hlen = 6 is what tells the server where the address stops.

08 Receive path

A filter in the kernel, a deadline in userspace, and four functions that walk the headers

Before anything is captured, a BPF program is compiled and installed so the kernel discards everything that is not a DHCP reply — on a busy segment this is the difference between four packets reaching userspace and forty thousand:

#define DHCP_CAPTURE_FILTER  "udp and src port 67 and dst port 68"

pcap_lookupnet(dev, &net, &mask, errbuf);   // mask only matters for "net" rules
pcap_compile(handle, &filter, DHCP_CAPTURE_FILTER, 1, mask);
pcap_setfilter(handle, &filter);
pcap_freecode(&filter);

If pcap_lookupnet() fails — which it does on an interface with no address yet, exactly the situation here — the mask falls back to PCAP_NETMASK_UNKNOWN rather than aborting, because this particular filter never references a network.

The loop has a deadline

static int wait_for_offer(pcap_t *handle, int timeout_sec)
{
    time_t deadline = time(NULL) + timeout_sec;

    while (ip == 0 && time(NULL) < deadline) {
        int count = pcap_dispatch(handle, 16, ether_input, NULL);

        if (count == -1) { /* capture failed */ return -1; }
        if (count == -2) break;      // pcap_breakloop() from dhcp_input
    }

    return ip != 0 ? 0 : -1;
}

pcap_dispatch() rather than pcap_loop() is the whole point: it returns after the current buffer of packets — or after the handle's 100 ms read timeout expires with nothing — which gives the while a chance to re-check the clock. pcap_loop() would block indefinitely on a network with no DHCP server, taking the GUI's worker thread and its communicate() call down with it. Ten seconds, then dhcpClientRenew() returns non-zero and main retransmits once.

Four handlers, one check each

ether_input()  // caplen sane? ntohs(ether_type) == ETHERTYPE_IP ?
   └─ ip_input()     // ip_p == IPPROTO_UDP ? advance by ip_hl * 4
        └─ udp_input()    // ntohs(uh_sport) == 67 ?
             └─ dhcp_input()   // opcode == BOOTREPLY ? xid == ours ?
                               //   → ip = ntohl(yiaddr); pcap_breakloop()

Each step validates before it casts one header deeper. ether_input() refuses a frame shorter than an Ethernet plus IP header, so a runt cannot make the next cast read off the end of the capture buffer. ip_input() advances by ip_hl * 4 instead of assuming 20, and rejects a header length below the struct size — a reply carrying IP options would otherwise land the UDP pointer inside the option block. And dhcp_input() checks two things: that the BOOTP opcode is DHCP_BOOTREPLY, and that the transaction ID matches the one this process generated. Without the second test, a DHCP reply meant for a different client on the same segment would be accepted as ours.

The retransmission keeps its transaction ID

When the first DISCOVER times out, main calls dhcpClientRenew() a second time. Both runs seed from time(NULL) ^ getpid() inside the same second and the same process, so the second attempt goes out under the same xid as the first — which is what RFC 2131 asks for. A retransmission is the same transaction, and a server that already answered should be able to recognise it as such.

Where the lease actually comes from

DHCP is a four-message exchange: DISCOVER → OFFER → REQUEST → ACK. This client sends the first and reads the second, then closes the pcap handle and returns. It does not send the REQUEST that formally claims the offered address, and does not wait for the ACK that binds the lease. So the line it prints —

printf("Got IP %u.%u.%u.%u\n", ip >> 24, (ip << 8) >> 24, (ip << 16) >> 24, (ip << 24) >> 24);

reports the address the server offered. The address the interface then settles on comes from the system's own DHCP client — dhcpcd, NetworkManager or systemd-networkd — which reacts to the link coming back up under a new MAC and runs the full four-message exchange itself. That division of labour is deliberate: fighting the system client for ownership of the lease is how you end up with two clients bidding for the same interface. PrivIP changes the identity and confirms, from the wire, that the network will hand that identity an address; binding it is the resolver's job.

Those bit shifts, incidentally, are correct only because ip was passed through ntohl() on receipt — it holds host order, so the most significant byte is the first octet.

09 Capabilities

Why this runs without sudo, and what it still can't do

Both halves of the binary need privilege: SIOCSIFHWADDR and SIOCSIFFLAGS require CAP_NET_ADMIN, and opening a packet socket for injection requires CAP_NET_RAW. Rather than setuid-root, the build attaches file capabilities:

sudo setcap 'cap_net_raw,cap_net_admin+ep' bin/privipchanger

The +ep suffix places both capabilities in the file's effective and permitted sets, so at execve the kernel grants exactly those two and nothing else — no root uid, no CAP_SYS_ADMIN, no ability to read /etc/shadow. The GUI can then Popen() it as a normal user and the child comes up privileged for precisely the two operations it needs.

Capabilities are attached to an inode, not a path

make writes a new file, and the new file has no xattrs — so every rebuild silently strips the capability set, and the next run fails with SIOCSIFHWADDR: Operation not permitted. That is why setcap is a Makefile target that all depends on, re-applied after every relink. It runs sudo -n, so on a machine with no cached credentials it declines to prompt and prints the command for you to run instead. The same inode rule applies to copying the binary, moving it across filesystems, or unpacking it from an archive.

Capabilities do not survive a Python re-exec

File caps are granted at execve of that file. The Python interpreter running dashboard.py has none; it only ever gains privilege in the child process it spawns. That is the right shape — the GUI stays unprivileged and the blast radius is one short-lived binary.

10 Python layer

A dashboard that reads sysfs, and a watchdog that polls the process table

dashboard.py — reading state without asking the binary

The GUI never parses the C program's output for state. It re-reads the truth from the kernel every five seconds via self.after(5000, …), Tk's event-loop timer — no thread, no blocking:

with open(f"/sys/class/net/{iface}/address") as f:
    mac = f.read().strip().upper()

res = subprocess.run(["ip", "-4", "addr", "show", iface],
                     capture_output=True, text=True)
match = re.search(r"\binet\s+(\d+\.\d+\.\d+\.\d+)", res.stdout)

The MAC read is exact — /sys/class/net/*/address is the kernel's own view, updated the instant the ioctl lands. The IP read shells out to ip, but as an argument list rather than a shell string, so the interface name is never re-parsed by /bin/sh; the address is picked out in Python with a plain re.search. Both reads catch OSError specifically rather than a bare except, which would have swallowed KeyboardInterrupt. The interface list comes from os.listdir('/sys/class/net/'), which is why the dropdown shows lo and any docker0 alongside your real NIC.

Running the binary is dispatched to a threading.Thread so the Tk main loop keeps painting, with Popen(...).communicate() collecting both streams and the exit code deciding what gets logged — a non-zero return prints identity NOT changed rather than a success line. That is the one place the two languages meet: argv[1] in, captured text and a status out.

The systemd unit is generated at runtime

Toggling the switch writes a user unit to ~/.config/systemd/user/privip-monitor.service and drives systemctl --user through three subprocess calls — daemon-reload, enable, start:

[Unit]
Description=PrivIP Firefox Watchdog
After=network.target

[Service]
ExecStart={self._service_python()} /path/to/src/monitor.py
Restart=always
RestartSec=5

[Install]
WantedBy=default.target
The unit runs the interpreter that has the dependencies

_service_python() resolves to .venv/bin/python when the virtualenv exists and falls back to sys.executable otherwise. Hardcoding /usr/bin/python3 — the obvious thing to write — would start a service that dies on import psutil, and with Restart=always and no RestartSec systemd would respawn it in a tight loop until the rate limiter tripped. Both halves of that are handled: the right interpreter, and a five-second restart delay.

monitor.py — edge detection on a 3-second poll

FIREFOX_NAMES = {"firefox", "firefox-bin", "firefox-esr"}
SETTLE_SECONDS = 5

firefox_was_running = False

while True:
    config = get_config()
    if config.get("auto_firefox", False):
        firefox_now = firefox_running()          # exact name match, not substring
        if firefox_now and not firefox_was_running:
            subprocess.run([BINARY, config.get("interface", "wlan0")])
            time.sleep(SETTLE_SECONDS)           # let the OS DHCP client re-lease
        firefox_was_running = firefox_now
    time.sleep(3)

This is a rising-edge detector, and the pattern is right: fire on the False → True transition, not on the level, or the identity would rotate every three seconds for as long as the browser is open. psutil.process_iter(['name']) walks /proc and caches only the name field, so the sweep is cheap. Matching against a set of exact process names rather than a "firefox" in name substring test keeps unrelated processes from triggering a rotation. Re-reading the JSON config each iteration means the GUI's switch takes effect without restarting the service.

The watchdog is a safety net, not the main workflow

The trigger fires when Firefox starts, and the interface is down for the few seconds the C binary runs — by which point the browser is already resolving its homepage, so the first page load after an automatic rotation may need a reload. Rotating first and launching the browser second is the smooth path, and the Force identity change button in the dashboard is there for exactly that. The watchdog covers the times you forget.

# V=1 shows the compiler invocations, and therefore the warnings
V ?= 0
ifeq ($(V),1)
Q :=
else
Q := @
endif

all: $(TARGET) setcap

$(BUILD_DIR)/%.o: $(CORE_DIR)/%.c
	$(Q)mkdir -p $(BUILD_DIR)
	$(Q)$(CC) $(CFLAGS) -c $< -o $@

-include $(DEPS)

Four things here are worth copying into other projects. $(wildcard) plus $(patsubst) means adding a .c file to core/ requires no Makefile edit. -MMD makes GCC emit a .d file listing every header the translation unit included, and -include $(DEPS) folds those rules back in — so editing include/dhcpClient.h correctly rebuilds only the objects that included it, and the leading - makes the include non-fatal on a clean tree where no .d files exist yet. all depends on setcap, so the capability set from section 09 is never left behind by a rebuild.

And the $(Q) indirection is the small one that matters most. Recipes prefixed with @ print nothing, which makes for a tidy build log and hides every compiler warning inside it. Here the prefix is a variable, so make V=1 restores the full invocations — the Linux kernel's convention, and the reason a warning in this tree gets seen rather than scrolled past.

-Wall -Wextra, and the build is clean

make clean && make V=1 on GCC produces no diagnostics across all three translation units. The pcap_handler signature forces an unused u_char *args parameter on ether_input(), which -Wextra would flag; it is silenced with an explicit (void)args; rather than by lowering the warning level.

Build from source rather than reaching for anything prebuilt in the tree: an object file compiled against a different libc or GCC version will not match, and per section 09 a binary that arrives by any route other than your own make carries no capabilities.

12 Scope

What it does, and what it deliberately leaves alone

This is a focused tool: it changes the two identifiers that name a machine on a LAN, and proves from the wire that the network will serve the new one. It is not a DHCP client, not a VPN, and not an anonymity layer above the link. Knowing where its edges are is part of understanding the problem it solves.

What it had to get right

DetailWhy it is easy to get wrong
Copy 6 bytes into a 16-byte chaddrThe field is 16 bytes and the source array is 6. Copying the size of the destination — the reflex — reads ten bytes off the end of the caller's stack and broadcasts them. hlen, not the field width, is what says where the address ends.
Fill the options before zeroing the headermemset(dhcp, 0, sizeof(dhcp_t)) stops at byte 240, exactly where bp_options[] begins. The order of those two calls is load-bearing, and reversing it produces a packet that still transmits.
Two bits of the first MAC octetBit 0 marks a multicast address and the kernel refuses it as a source; bit 1 declares the address locally administered. A randomiser that ignores them fails on roughly half its draws.
Match the transaction IDSeveral clients can be soliciting on one segment at once. Without the xid check, the first OFFER to arrive is accepted — including one meant for somebody else.
Bound the waitA capture loop with no deadline blocks forever on a network with no DHCP server, and takes the caller's thread down with it. pcap_dispatch() against a clock is what keeps it answerable.

Deliberate omissions

Named explicitly, because each one is a decision rather than an oversight.

Not implementedWhy
REQUEST / ACKBinding the lease is the system DHCP client's job, and two clients bidding for one interface is worse than either alone. See section 08.
Client-identifier and hostname optionsBoth are durable names for the machine. Sending either would re-establish exactly the link the MAC rotation just broke.
DHCPv6A separate protocol over UDP/546–547 with its own message set, and an IPv6 address that derives from the MAC anyway on a SLAAC network.
Persistence across rebootsThe address is drawn fresh per run by design; there is nothing to store, and storing it would be a file that outlives the identity it names.
NetworkManager integrationNM has its own wifi.cloned-mac-address machinery. Driving the ioctl directly is what makes the mechanism visible, which is the point of the exercise.

What this actually buys you

Randomising the hardware address and re-soliciting a lease genuinely severs one session from the next: there is nothing durable in the frame — no client identifier, no hostname, no vendor prefix — for a network to key on, so the device that connects this afternoon has no observable relationship to the one that connected this morning. That is unlinkability, and it is what the code delivers. It is not concealment: a DHCP server still sees a DISCOVER arrive and still logs the address it hands out. The right way to use it is as a reset button on the identity a network knows you by, on networks where you are entitled to press it.

13 Running it

Build, grant, launch

# everything at once: deps, make, setcap, virtualenv
./scripts/install.sh

# or by hand — deps first (Arch shown; the script also handles apt and dnf)
sudo pacman -S --needed base-devel libpcap python python-pip tk libcap

# build the C engine → bin/privipchanger, and apply the capabilities
make

# python side
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt

GUI

./cprivip.sh — activates the venv and launches the dashboard. Live MAC/IP readout, interface picker, manual rotate, watchdog toggle, log pane.

CLI

./bin/privipchanger wlan0 — one rotation. Exits non-zero if the MAC rewrite fails or no offer arrives within two attempts.

Service

systemctl --user status privip-monitor and journalctl --user -u privip-monitor -f.

Verify

ip link show wlan0 for the MAC, ip -4 addr show wlan0 for the lease. The offered address the binary prints is not proof of the address you hold.

Let NetworkManager know whose address it is

On a managed system, taking the interface down and back up hands control to NetworkManager, which applies its own wifi.cloned-mac-address policy on reconnect and may overwrite what you just set. If the MAC reverts within a second of a rotation, that is why — set wifi.cloned-mac-address=permanent for the connection, or unmanage the device, and the address PrivIP installs is the one that stays.

Use this on networks you own or are authorized to test. Rotating a hardware address to defeat a captive portal's usage accounting is, in most jurisdictions, a terms-of-service violation at minimum.

The DHCP transmit and receive path in dhcpClient.c derives from Samuel Jacob's Simple DHCP Client (BSD); the BPF filter, the bounded capture loop, the transaction matching and the bounds checks are changes on top of it. MAC randomisation, GUI, watchdog and build system are original. The field offsets and the hexdump in section 07 were produced by linking the current source against a stub pcap_inject().
