Rotating a machine's network identity, one ioctl and one injected frame at a time

A Linux utility that rewrites a NIC's hardware address and hand-builds the DHCP DISCOVER that follows it.

Two identifiers name you on a LAN, and they live at different layers. PrivIP rewrites the first through the kernel's ioctl configuration interface, then assembles a 300-byte Ethernet frame in a stack buffer and puts it on the wire with pcap_inject() — no socket, no kernel UDP stack, no DHCP client. This is a byte-level walkthrough of how it does that, what it gets right, and where the implementation lies to you.

01 The problem

Two addresses identify you on a LAN, and they live at different layers

When a laptop joins a network it presents two identifiers. The first is the MAC address — 48 bits burned into the NIC, visible to every device in the broadcast domain, never routed past the first hop. The second is the IP address — leased from a DHCP server, and in practice keyed to the MAC that asked for it.

A captive portal that counts your 30 free minutes remembers a MAC. A DHCP server that hands you the same 192.168.1.47 every morning does so because it remembers a MAC. Change the first identifier and the second follows; the network sees a device it has never met.

PrivIP does exactly that, in two moves. It rewrites the interface's hardware address through the kernel's ioctl configuration interface, then — instead of asking the system's DHCP client to renew — it builds a 300-byte Ethernet frame in a stack buffer and shoves it onto the wire with pcap_inject().

Layer 2

48 bit

Hardware address, rewritten via SIOCSIFHWADDR while the link is down.

Layer 3

32 bit

Leased address, re-solicited by a hand-built DHCP DISCOVER broadcast.

Injected frame

300 B

14 Ethernet + 20 IP + 8 UDP + 240 BOOTP + 18 options.

Privilege

2 caps

cap_net_raw to inject, cap_net_admin to reconfigure the link.

Why not just call dhclient

You could. The point of the exercise is that the DHCP client here is not a client in the OS sense — there is no AF_INET socket, no bind() to port 68, no kernel UDP stack involvement on transmit. The frame is assembled byte by byte and handed to the driver. That makes it a teaching artifact for packet construction as much as a privacy tool.

03 Entry point

Fifteen lines that set the whole sequence

/* core/main.c */
int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "Incorrect argument number, just one interface please\n");
        return 1;
    }

    changeMac(2, argv);          // L2: down → increment → up
    dhcpClientRenew(2, argv);    // "set to 0.0.0.0"
    dhcpClientRenew(2, argv);    // "get new IP addr"
    return 0;
}

Both subsystems take (int argc, char **argv) rather than a plain interface string. That is a deliberate shim: dhcpClient.c is a lightly-modified copy of Samuel Jacob's BSD-licensed Simple DHCP Client, whose main() was renamed to dhcpClientRenew() with its CLI parsing left intact. So the interface name arrives as argv[1] in both, and both still print their own usage string.

Return values discarded

changeMac() returns 1 on any failure and main ignores it. If the MAC rewrite fails — wrong interface name, missing CAP_NET_ADMIN, a driver that refuses SIOCSIFHWADDR — the program proceeds to broadcast two DISCOVERs from the old MAC and exits 0. The caller, including the GUI, is told everything worked.

The comments overstate the code

Neither call "sets to 0.0.0.0". Both invocations run the identical code path: open pcap, send one DISCOVER, block until a BOOTREPLY arrives. The double call is a retransmission, not a two-phase release-then-acquire. Nothing in this binary ever sends a DHCPRELEASE or a DHCPREQUEST.

04 MAC rotation

Three ioctls on a throwaway datagram socket

There is no syscall named "set MAC address". Link configuration on Linux rides on ioctl() against any socket file descriptor — the socket is never used for traffic, it exists only as a handle into the networking subsystem. The whole module opens socket(AF_INET, SOCK_DGRAM, 0) and issues requests against it.

The request payload is struct ifreq: a fixed 16-byte interface name (IFNAMSIZ) followed by a large union whose active member depends on which request code you pass.

Step 1 — take the link down SIOCSIFFLAGS

ioctl(sock, SIOCGIFFLAGS, &ifr);      // read current flags
if (state) ifr.ifr_flags |=  IFF_UP;
else       ifr.ifr_flags &= ~IFF_UP;
ioctl(sock, SIOCSIFFLAGS, &ifr);      // write them back

Read-modify-write, not blind assignment — clobbering the flag word would drop IFF_BROADCAST, IFF_MULTICAST and friends. The link must be administratively down first: most drivers return EBUSY from SIOCSIFHWADDR on a running interface, because the address is programmed into the hardware receive filter.

Step 2 — read, increment, write SIOCSIFHWADDR

ioctl(sock, SIOCGIFHWADDR, &ifr);
memcpy(currentMac, ifr.ifr_hwaddr.sa_data, 6);

memcpy(newMac, currentMac, 6);
int carry = 1;
for (i = 5; i >= 0; i--) {
    int sum = (unsigned char)newMac[i] + carry;
    newMac[i]  = sum & 0xFF;
    carry      = sum >> 8;
    if (carry == 0) break;
}
if (carry) memset(newMac, 0, 6);       // FF:FF:...:FF wrapped

ifr.ifr_hwaddr.sa_family = ARPHRD_ETHER;
memcpy(ifr.ifr_hwaddr.sa_data, newMac, 6);
ioctl(sock, SIOCSIFHWADDR, &ifr);

This is a big-endian 48-bit increment done by hand: iterate from the least significant octet, propagate carry, early-exit the instant carry clears — so the common case touches exactly one byte. sa_family must be set to ARPHRD_ETHER (1) on the way in or the kernel rejects the request with EINVAL; the getter leaves it populated, but the code sets it explicitly anyway.

Sequential addresses are a fingerprint

Incrementing the last octet preserves the top 24 bits — the OUI — so the network still knows the vendor of your card, and an observer that logs …:2b:c8 then …:2b:c9 then …:2b:ca can trivially link the sessions. It also never forces bit 1 of octet 0 (the locally-administered bit) or clears bit 0 (the multicast bit); an increment that lands on an odd first octet produces a multicast address the kernel will refuse. A randomized address with mac[0] = (rand() & 0xFC) | 0x02 would be both safer and less linkable.

Descriptor leak on the error path

setInterfaceState() returns -1 after a failed SIOCSIFFLAGS without calling close(sock). Short-lived process, so it never matters in practice — but it is the one path in the file that forgets.

Step 3 — bring it back up

The same setInterfaceState(iface, 1). On Wi-Fi this is where reality intrudes: taking wlan0 down tears down the association, and on a NetworkManager system the daemon will notice the carrier flap and start its own reconnect — potentially reprogramming the MAC (NM's own wifi.cloned-mac-address policy) and running its internal DHCP client. The C code has no idea any of that is happening.

05 The frame

Building outward from the middle of a 4 KB stack buffer

The transmit path is written inside-out, and the ordering is load-bearing. A single u_char packet[4096] lives on dhcp_discovery()'s stack; three pointers are computed into it at fixed offsets, and each layer's writer both fills its header and grows a shared length counter.

static int dhcp_discovery(u_int8_t *mac)
{
    int len = 0;
    u_char packet[4096];                         // uninitialised

    ip_header  = (struct ip *)      (packet + sizeof(struct ether_header));
    udp_header = (struct udphdr *)  ((char *)ip_header  + sizeof(struct ip));
    dhcp       = (dhcp_t *)          ((char *)udp_header + sizeof(struct udphdr));

    len = fill_dhcp_discovery_options(dhcp);     // +18  → 18
    dhcp_output(dhcp, mac, &len);                // +240 → 258
    udp_output(udp_header, &len);                // +8   → 266
    ip_output(ip_header, &len);                  // +20  → 286
    ether_output(packet, mac, len);              // +14  → 300, inject
    return 0;
}

Payload first, headers after — the same discipline a kernel uses, because every header needs the length of everything beneath it. ip_output() cannot fill ip_len until UDP has added its 8 bytes, and UDP cannot fill uh_ulen until the BOOTP body and its options are sized.

Options are written before the header is zeroed

Look closely at the first two calls. fill_dhcp_discovery_options() writes into dhcp->bp_options[] — a zero-length flexible array member sitting at byte 240 of the struct. Then dhcp_output() runs memset(dhcp, 0, sizeof(dhcp_t)), which clears bytes 0–239 only. The options survive because sizeof(dhcp_t) stops exactly where they begin. Reverse those two lines and the packet still transmits, silently, with its options intact but its BOOTP header wiped — a bug that would only show up on the wire.

Each writer, in the order they run

fill_dhcp_option — the TLV primitive DHCP

static int fill_dhcp_option(u_int8_t *packet, u_int8_t code,
                            u_int8_t *data, u_int8_t len)
{
    packet[0] = code;
    packet[1] = len;
    memcpy(&packet[2], data, len);
    return len + (sizeof(u_int8_t) * 2);
}

Classic tag-length-value, returning bytes consumed so the caller can advance its cursor. Four options are emitted: message type 53 = DISCOVER, requested-IP 50, parameter-request-list 55 asking for subnet mask / router / DNS / domain name, and the terminator.

udp_output — the alignment nudge UDP

if (*len & 1) *len += 1;              // pad payload to even
*len += sizeof(struct udphdr);
udp_header->uh_sport = htons(68);
udp_header->uh_dport = htons(67);
udp_header->uh_ulen  = htons(*len);
udp_header->uh_sum   = 0;             // legal on IPv4

The odd-length pad exists because the one's-complement checksum routine consumes 16-bit words. Here it is dead code — 240 + 18 = 258 is already even — but it is the correct instinct. A zero UDP checksum is permitted over IPv4 and means "not computed"; over IPv6 it would be illegal.

ip_output — a hand-rolled IPv4 header IPv4

ip_header->ip_hl  = 5;                // 5 × 4 = 20 bytes, no options
ip_header->ip_v   = IPVERSION;        // 4
ip_header->ip_tos = 0x10;             // low delay
ip_header->ip_len = htons(*len);      // 286
ip_header->ip_id  = htons(0xffff);    // constant — a fingerprint
ip_header->ip_off = 0;
ip_header->ip_ttl = 16;
ip_header->ip_p   = IPPROTO_UDP;
ip_header->ip_sum = 0;
ip_header->ip_src.s_addr = 0;             // 0.0.0.0, we have no lease
ip_header->ip_dst.s_addr = 0xFFFFFFFF;    // 255.255.255.255
ip_header->ip_sum = in_cksum((unsigned short *)ip_header, sizeof(struct ip));

Source 0.0.0.0 is mandatory here and is precisely why this cannot go through a normal socket: the host has no address yet, so it identifies itself only by the chaddr field inside the DHCP body. Note the checksum field is zeroed before being summed — required, since the checksum covers itself.

in_cksum() is the FreeBSD one's-complement routine, verbatim: accumulate 16-bit words into a 32-bit sum, fold the carries down twice, invert. For this header the result is 0xA9C0.

ether_output — and out L2

memcpy(eframe->ether_shost, mac, ETHER_ADDR_LEN);
memset(eframe->ether_dhost, -1,  ETHER_ADDR_LEN);   // ff:ff:ff:ff:ff:ff
eframe->ether_type = htons(ETHERTYPE_IP);
len += sizeof(struct ether_header);
result = pcap_inject(pcap_handle, frame, len);

memset(dst, -1, 6) is the idiomatic way to write the broadcast address: -1 truncated to unsigned char is 0xFF. pcap_inject() hands the finished 300 bytes straight to the driver's transmit queue — no routing lookup, no ARP, no kernel checksum offload. Whatever is in the buffer is what leaves the machine.

06 Byte layout

Where every field lands in the 300-byte frame

The BOOTP fixed header is 236 bytes, followed by the 4-byte magic cookie, followed by variable options — which puts bp_options[0] at offset 240 within the DHCP body, exactly as RFC 2131 requires. The struct in dhcpClient.c reproduces that layout with no padding because every member is naturally aligned.

Two spec deviations in three bytes

Option 255 is a bare terminator with no length or value field — RFC 2132 is explicit. Sending ff 01 00 works because every parser stops at the 0xFF and ignores the trailing bytes as padding, but it is wrong. And requesting 192.168.1.10 on every network is at best ignored and at worst an unsolicited claim on someone else's address; a real client either omits option 50 in DISCOVER or asks for its previous lease.

Ten bytes of your stack, broadcast to the LAN

dhcp_output() does memcpy(dhcp->chaddr, mac, DHCP_CHADDR_LEN) — 16 bytes copied out of a u_int8_t mac[6] that lives on dhcpClientRenew()'s frame. Ten bytes past the end of the array are read and transmitted at offset 0x46. On the destination side the bytes are harmless: hlen = 6 tells the server to ignore everything past the sixth. On the source side it is an out-of-bounds read and a stack-memory disclosure to every host in the broadcast domain, and exactly the kind of thing ASAN flags on the first run. The fix is one constant: copy 6, and let the surrounding memset supply the padding.

08 Receive path

A callback chain that re-implements the protocol stack in four functions

After injection the program blocks in pcap_loop(pcap_handle, -1, ether_input, NULL) — capture forever, calling ether_input per frame. Each handler does a single check and casts one header deeper.

ether_input()  // eframe->ether_type == ETHERTYPE_IP ?
   └─ ip_input()     // ip_p == IPPROTO_UDP ?
        └─ udp_input()    // ntohs(uh_sport) == 67 ?
             └─ dhcp_input()   // opcode == 2 ? → ip = ntohl(yiaddr); pcap_breakloop()

Every step advances by sizeof of the header it just validated. That is fine for this program — the injected DISCOVER guarantees a fixed-shape reply — but it is the shortcut that turns a parser into a vulnerability in the general case: ip_input assumes a 20-byte IPv4 header rather than reading ip_hl, so a reply carrying IP options would land the UDP pointer inside the option block.

Correct by coincidence, twice

dhcp_input() tests dhcp->opcode != DHCP_OPTION_OFFER. That constant is 2 — but it belongs to the option 53 message-type namespace, while opcode holds a BOOTP operation code. The comparison only works because DHCP_BOOTREPLY also happens to equal 2. Separately, ether_input() writes htons(eframe->ether_type) == ETHERTYPE_IP where it means ntohs; on any little-endian host the two are the identical byte swap, so it passes. Both would break the moment the code is ported or the constants are renumbered.

No filter, no timeout, no transaction matching

Three omissions compound here. There is no pcap_setfilter(), so every frame on the segment is copied to userspace and — at the default VERBOSE_LEVEL_DEBUG — hexdumped to stdout, which on a busy Wi-Fi network is thousands of lines before the OFFER arrives. There is no xid check, so a DHCP reply meant for a different client on the same segment is accepted as ours. And pcap_loop(-1) has no timeout: on a network with no DHCP server the process blocks forever, taking the GUI's worker thread and process.communicate() with it. A BPF program of udp and src port 67 plus an alarm or a bounded packet count would fix all three.

The handshake that isn't

DHCP is a four-message exchange: DISCOVER → OFFER → REQUEST → ACK. This client sends the first and reads the second, then closes the pcap handle and returns. It never sends the REQUEST that formally claims the offered address, and never waits for the ACK that binds the lease. So the line it prints —

printf("Got IP %u.%u.%u.%u\n", ip >> 24, (ip << 8) >> 24, (ip << 16) >> 24, (ip << 24) >> 24);

reports an address that was offered, not one the machine holds. The address the interface actually ends up with comes from the system's own DHCP client (dhcpcd, NetworkManager, systemd-networkd) reacting to the link coming back up with a new MAC. PrivIP's real contribution to the IP change is step 04; the injected frame is a probe, and an excellent one to learn from, but the lease is somebody else's work.

Those bit shifts, incidentally, are correct only because ip was passed through ntohl() on receipt — it holds host-order, so the most significant byte is the first octet.

09 Capabilities

Why this runs without sudo, and what it still can't do

Both halves of the binary need privilege: SIOCSIFHWADDR and SIOCSIFFLAGS require CAP_NET_ADMIN, and opening a packet socket for injection requires CAP_NET_RAW. Rather than setuid-root, the installer attaches file capabilities:

sudo setcap 'cap_net_raw,cap_net_admin+ep' bin/privipchanger

The +ep suffix places both capabilities in the file's effective and permitted sets, so at execve the kernel grants exactly those two and nothing else — no root uid, no CAP_SYS_ADMIN, no ability to read /etc/shadow. The GUI can then Popen() it as a normal user and the child comes up privileged for precisely the two operations it needs.

Capabilities are attached to an inode, not a path

make writes a new file, and the new file has no xattrs. Every rebuild silently strips the capability set, and the next run fails with SIOCSIFHWADDR: Operation not permitted from perror. Re-run the setcap line after any build — or add it as a Makefile recipe step, which is the durable fix. The same applies to copying the binary, moving it across filesystems, or unpacking it from an archive.

Capabilities do not survive a Python re-exec

File caps are granted at execve of that file. The Python interpreter running dashboard.py has none; it only ever gains privilege in the child process it spawns. That is the right shape — the GUI stays unprivileged and the blast radius is one short-lived binary.

10 Python layer

A dashboard that reads sysfs, and a watchdog that polls the process table

dashboard.py — reading state without asking the binary

The GUI never parses the C program's output for state. It re-reads the truth from the kernel every five seconds via self.after(5000, …), Tk's event-loop timer — no thread, no blocking:

with open(f"/sys/class/net/{iface}/address") as f:
    mac = f.read().strip().upper()

cmd = f"ip -4 addr show {iface} | grep -oP '(?<=inet\\s)\\d+(\\.\\d+){{3}}' | head -n 1"
res = subprocess.run(cmd, shell=True, capture_output=True, text=True)

The MAC read is exact — /sys/class/net/*/address is the kernel's own view, updated the instant the ioctl lands. The IP read shells out to ip and scrapes it with a PCRE lookbehind. The interface list comes from os.listdir('/sys/class/net/'), which is why the dropdown shows lo and any docker0 alongside your real NIC.

shell=True on a value that comes from sysfs

The interface name is interpolated into a shell string. It originates from a directory listing of /sys/class/net/, so in practice it cannot contain a metacharacter — but the safe form costs nothing: subprocess.run(["ip","-4","addr","show",iface]) and parse in Python, or skip the subprocess entirely and read /proc/net/fib_trie. The same applies to the bare except: clauses around both reads, which will swallow a KeyboardInterrupt.

Running the binary is dispatched to a threading.Thread so the Tk main loop keeps painting, with Popen(...).communicate() collecting both streams. That is the one place the two languages meet: argv[1] in, captured text out, appended to the log box.

The systemd unit is generated at runtime

Toggling the switch writes a user unit to ~/.config/systemd/user/privip-monitor.service and drives systemctl --user through three subprocess calls — daemon-reload, enable, start:

[Unit]
Description=PrivIP Firefox Watchdog
After=network.target

[Service]
ExecStart=/usr/bin/python3 /path/to/src/monitor.py
Restart=always

[Install]
WantedBy=default.target
The unit runs the system interpreter, not the venv

ExecStart is hardcoded to /usr/bin/python3, while psutil was installed into .venv by the installer. Unless psutil also happens to be present system-wide, the service dies on ImportError at import time — and because Restart=always has no RestartSec, systemd restarts it in a tight loop until the rate limiter trips. The GUI's check_service_status() reports it as inactive with no explanation. Point ExecStart at {base_dir}/.venv/bin/python and the whole class of failure disappears.

monitor.py — edge detection on a 3-second poll

firefox_was_running = False

while True:
    config = get_config()
    if config.get("auto_firefox", False):
        firefox_now = any("firefox" in p.name().lower()
                          for p in psutil.process_iter(['name']))
        if firefox_now and not firefox_was_running:
            subprocess.run([BINARY, config.get("interface", "wlan0")])
        firefox_was_running = firefox_now
    time.sleep(3)

This is a rising-edge detector, and the pattern is right: fire on the False → True transition, not on the level, or the identity would rotate every three seconds for as long as the browser is open. psutil.process_iter(['name']) walks /proc and caches only the name field, so the sweep is cheap. Re-reading the JSON config each iteration means the GUI's switch takes effect without restarting the service.

Rotating the network out from under the browser

The trigger fires when Firefox starts, and subprocess.run() then takes the interface down for the duration of the C binary — several seconds, plus however long the OS DHCP client needs to re-lease. Firefox is by then already resolving its homepage. The first page load after an auto-rotation frequently fails. Firing on the edge and then waiting for the link to settle before returning would be the honest behaviour; a small sleep after the binary exits is the one-line version. The substring match is also broad — firefox-esr, firefoxdeveloperedition, and any process with "firefox" in its name all count.

11 Build system

Pattern rules and compiler-generated dependencies

CFLAGS  := -Wall -Wextra -O3 -I$(INC_DIR) -MMD
LDFLAGS := -lpcap

SRCS := $(wildcard $(CORE_DIR)/*.c)
OBJS := $(patsubst $(CORE_DIR)/%.c, $(BUILD_DIR)/%.o, $(SRCS))
DEPS := $(OBJS:.o=.d)

$(BUILD_DIR)/%.o: $(CORE_DIR)/%.c
	@mkdir -p $(BUILD_DIR)
	@$(CC) $(CFLAGS) -c $< -o $@

-include $(DEPS)

Three things here are worth copying into other projects. $(wildcard) plus $(patsubst) means adding a .c file to core/ requires no Makefile edit. -MMD makes GCC emit a .d file listing every header the translation unit included, and -include $(DEPS) folds those rules back in — so editing include/dhcpClient.h correctly rebuilds only the objects that included it. The leading - makes the include non-fatal on a clean tree where no .d files exist yet.

-Wall -Wextra is on, and the build is not clean

Two of the warnings the flags produce point at real defects. dhcpClientRenew() jumps to its done: label with result holding the DISCOVER return code, so a successful run returns 0 through a path labelled as failure handling. And ether_input() takes u_char *args — required by the pcap_handler signature — which -Wextra flags as unused. The @ prefix on every recipe line hides the compiler invocation, so those warnings scroll past under a tidy "Compiled:" line. Dropping the @ during development is worth the noise.

One structural note: make clean removes build/ and the binary but the repository ships both build/*.o and bin/* committed. Prebuilt objects in version control will not match a different libc or GCC version, and — per section 09 — the committed binary carries no capabilities. Build from source.

What a network operator sees

Worth stating plainly, since the tool's stated purpose is privacy. The DISCOVER this program emits is highly distinctive: xid = 0, ip_id = 0xffff, ttl = 16, tos = 0x10, a 3-byte end option, a fixed requested-IP of 192.168.1.10, and no client-identifier or hostname option at all. Any DHCP server with logging, or any IDS with a fingerprint database, can pick these packets out of normal traffic immediately — and correlate them with the sequential MAC addresses from section 04. As a privacy mechanism the MAC rotation is real but weakly implemented; as a demonstration of raw packet construction the code is a good, compact read.

13 Running it

Build, grant, launch

# dependencies (Debian/Ubuntu; on Arch: pacman -S base-devel libpcap tk)
sudo apt install build-essential libpcap-dev python3-venv python3-tk

# build the C engine → bin/privipchanger
make

# grant the two capabilities — repeat after every rebuild
sudo setcap 'cap_net_raw,cap_net_admin+ep' bin/privipchanger

# python side
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt

GUI

./cprivip.sh — activates the venv and launches the dashboard. Live MAC/IP readout, interface picker, manual rotate, watchdog toggle, log pane.

CLI

./bin/privipchanger wlan0 — one rotation, verbose. Add | head -40 unless you want every frame on the segment hexdumped.

Service

systemctl --user status privip-monitor and journalctl --user -u privip-monitor -f.

Verify

ip link show wlan0 for the MAC, ip -4 addr show wlan0 for the lease. Confirm both changed — the binary's own success message does not prove it.

Expect NetworkManager to argue

On a managed system, taking the interface down and back up hands control to NetworkManager, which may apply its own wifi.cloned-mac-address policy and overwrite what you just set. If the MAC reverts within a second of the rotation, that is why — set wifi.cloned-mac-address=permanent for the connection, or unmanage the device, before concluding the ioctl failed.

Use this on networks you own or are authorized to test. Rotating a hardware address to defeat a captive portal's usage accounting is, in most jurisdictions, a terms-of-service violation at minimum.
